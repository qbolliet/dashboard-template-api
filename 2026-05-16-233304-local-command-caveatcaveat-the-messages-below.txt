     Plan : CI/CD complète, pre-commit et versioning automatisé

     Contexte

     L'API dashboard-template-api est destinée à être réutilisée comme template 
     dans d'autres projets. L'objectif est de la professionnaliser via :
     - une CI qui garantit la qualité (lint, format, typecheck, tests) sur
     chaque PR et push main,
     - un système de release automatisé basé sur les Conventional Commits (déjà
     utilisés dans l'historique) qui maintient un CHANGELOG.md et crée les tags
     v*.*.*,
     - des pre-commit hooks qui rattrapent les erreurs avant la CI,
     - la publication automatique de l'image Docker (GHCR), du chart Helm et de
     la documentation (GitHub Pages).

     État actuel — 4 workflows déjà fonctionnels (test.yml, build-image.yml,
     docs.yml, release-chart.yml). Les triggers sont cohérents : push main +
     tags v*.*.*. Il manque essentiellement la couche qualité côté développeur
     (hooks, format check, commitlint) et l'automatisation des releases
     (CHANGELOG, bump de version, déclenchement coordonné des tags).

     ---
     Réponses à tes questions

     Tags + CHANGELOG : oui, c'est l'approche standard

     Pour une API réutilisée en template, c'est même essentiel :
     - Les consommateurs ont besoin de pinner une version
     (ghcr.io/.../dashboard-template-api:v1.2.3)
     - Le CHANGELOG documente les breaking changes (critique pour SemVer)
     - Le tag v*.*.* est déjà le déclencheur de build-image.yml et
     release-chart.yml — donc on s'aligne dessus

     Versionner images et déploiements : oui, déjà en place

     build-image.yml génère déjà :
     - latest (sur main)
     - sha-<short> (traçabilité)
     - v1.2.3, 1.2 (semver à partir du tag)

     Le chart Helm est lui aussi publié sur tag via chart-releaser-action. Il
     manque juste la synchronisation automatique entre tag git,
     package.json:version, et helm/dashboard-template-api/Chart.yaml:appVersion.
      C'est le rôle de release-please.

     3. release-please — .github/workflows/release-please.yml

     Pourquoi : lit les Conventional Commits sur main, maintient une PR de
     release qui bumpe package.json ET helm/dashboard-template-api/Chart.yaml
     (version + appVersion), et écrit CHANGELOG.md. Quand cette PR est mergée,
     le tag v*.*.* est créé → cela déclenche automatiquement build-image.yml et
     release-chart.yml (déjà configurés sur ce trigger).

     name: Release Please

     on:
       push:
         branches: [main]

     permissions:
       contents: write
       pull-requests: write

     jobs:
       release-please:
         runs-on: ubuntu-latest
         steps:
           - uses: googleapis/release-please-action@v4
             with:
               config-file: .release-please-config.json
               manifest-file: .release-please-manifest.json

     .release-please-config.json (racine) — bump synchronisé Node + Helm :
     {
       "release-type": "node",
       "packages": {
         ".": {
           "release-type": "node",
           "package-name": "dashboard-template-api",
           "changelog-path": "CHANGELOG.md",
           "extra-files": [
             {
               "type": "yaml",
               "path": "helm/dashboard-template-api/Chart.yaml",
               "jsonpath": "$.version"
             },
             {
               "type": "yaml",
               "path": "helm/dashboard-template-api/Chart.yaml",
               "jsonpath": "$.appVersion"
             }
           ]
         }
       },
       "include-component-in-tag": false,
       "bootstrap-sha": "354227f"
     }

     .release-please-manifest.json (racine, initial) :
     { ".": "0.1.0" }

     4. Étendre .github/workflows/test.yml

     Ajouter deux étapes au job test existant :

     - name: Format check (Prettier)
       run: npm run format:check
     (à insérer juste après "Lint")

     Et ajouter un second job commitlint qui s'exécute uniquement sur les PRs :

       commitlint:
         if: github.event_name == 'pull_request'
         runs-on: ubuntu-latest
         steps:
           - uses: actions/checkout@v4
             with: { fetch-depth: 0 }
           - uses: actions/setup-node@v4
             with: { node-version: 20, cache: npm }
           - run: npm ci
           - name: Validate commit messages
             run: npx commitlint --from ${{ github.event.pull_request.base.sha
     }} --to ${{ github.event.pull_request.head.sha }} --verbose

     Conflit potentiel à anticiper : GitHub Pages

     docs.yml publie via actions/deploy-pages (source : GitHub Actions), tandis
     que release-chart.yml publie le chart sur la branche gh-pages-charts via
     chart-releaser-action. Comme les deux ciblent GitHub Pages, vérifier dans
     Settings → Pages que la source est bien GitHub Actions (pas une branche),
     sinon le chart écrasera le site Docusaurus. Le chart est accessible via la
     branche gh-pages-charts séparément (URL helm repo add ... 
     https://<user>.github.io/<repo>/).

     Action : pas de fichier à créer, mais à valider manuellement dans les
     Settings du repo après le premier déploiement.

     ---
     Vérification end-to-end

     1. Pre-commit : faire un commit avec une erreur de format ESLint → doit
     échouer au pre-commit. Tenter un commit message non-conventional (update 
     stuff) → doit échouer au commit-msg. Tenter un push avec une erreur TS →
     doit échouer au pre-push.
     2. CI sur PR : ouvrir une PR avec un mauvais format Prettier → l'étape
     format:check doit fail. Un commit non-conventional → le job commitlint doit
      fail.
     3. Release : merger un feat: ... sur main → une PR "chore(main): release
     X.Y.Z" doit apparaître dans les minutes qui suivent, avec un CHANGELOG.md
     généré et les versions package.json + Chart.yaml bumpées.
     4. Cascade tag : merger la release PR → vérifier que :
       - le tag v*.*.* est créé,
       - build-image.yml se déclenche et publie sur
     ghcr.io/<owner>/dashboard-template-api:v*.*.*,
       - release-chart.yml se déclenche et publie le chart sur gh-pages-charts.
     5. Docs : indépendant du tag — chaque push main redéploie la doc, à valider
      via https://<owner>.github.io/dashboard-template-api/.
